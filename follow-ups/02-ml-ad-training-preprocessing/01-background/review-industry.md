## 2. Thematic synthesis (every theme mapped to PIPELINE QUESTIONS P-A–P-F)

### T-P1. Production training pipelines are staged jobs with versioned artifacts — the stage list is stable across sources [→ P-A, P-F]

Consensus (HIGH): independent practitioner builds converge on the same stage sequence — ingest → clean (dropout fill, timestamp alignment, dedupe) → state-filter (remove maintenance/shutdown periods from training) → normalize (fit-on-train-only scalers) → window (fixed windows, overlap) → feature (time + spectral) → temporal split → train → threshold-tune → register → shadow → serve → monitor [J12, J15, J16, J09].
- The stage list is explicit in the ops-platform build guide [J12]: 6–12 months clean data in, known-anomalous periods (faults, shutdowns, planned maintenance) OUT of the training set, hold out most-recent 20% for validation, measure detection rate + FP rate + lead time.
- OSS pipeline repos emit the same artifacts we will need: `scaler.pkl` (fitted normalization object), `window_config.json` (window/step + split ratios), `X_train/val/test` arrays, `ingestion_metadata.json` [J16-snippet]. The dual-pipeline feature-store pattern (same features offline and online) exists specifically to kill training-serving skew [J09-snippet].
- Multi-modal alignment is a first-class job, not an afterthought: vibration 10 kHz → 1 Hz features (RMS/peak/crest + Welch PSD bands), temperature forward-filled, current averaged, outer-joined on a common clock, with a `days_to_maintenance` target column and anomaly-back-labeling from failure events [J15]. Data archaeology consumed 40% of that project's timeline — misaligned timestamps, SCADA restart gaps, forgotten defect codes.
- Ownership pattern: data-layer jobs (ingest/clean/align) owned by data/OT engineering, training/eval jobs owned by ML, promotion owned by a gate (human or policy), monitoring owned by on-call [J09-snippet, J11, J13].
- P-A answer: our pipeline needs exactly these jobs — `acquire` (twin export + future real ingest), `clean` (dropout flags, timestamp checks), `state_filter` (STARVED/BLOCKED/DOWN + MAINT_EVENT handling), `normalize` (persist fitted scaler), `window` (persist window config), `feature` (time + spectral), `split` (episode/seed-grouped), `train`, `calibrate` (threshold tune), `register` (MLflow), `shadow`, `monitor`. Each emits a versioned artifact; the registry entry links model → dataset version → code commit [J04].

### T-P2. Labeling with scarce faults: maintenance-window labels + operator-code audit + feedback loop, weak supervision as the documented upgrade [→ P-B]

Consensus (HIGH on window-labeling + feedback loop; MEDIUM on weak-supervision specifics):
- Pre/post-maintenance window labeling is the production standard this extends from T4: label pre-maintenance windows anomalous / post-maintenance normal [01-I11]; the platform guide [J12] operationalizes it as "remove known anomalous periods from training; steady-state only is the baseline."
- Operator-code audit is the label substrate AND the #1 complaint (extends T4 [01-I12/I13]): maintenance records are inconsistent (precise timestamps vs shift-only discovery notes), so the Fortune-500 deployment built an anomaly-back-labeling algorithm extending labels from failure point back to earliest detectable precursor [J10]. Our free sim labels (`faults[]`) remain a structural advantage practitioners wish they had.
- The feedback loop is the highest-leverage labeling investment: every confirmed failure feeds back as a labeled example; technician close-out dispositions (found-degradation Y/N) flow into retraining; precision rose 91% → 94% over 12 months on outcome data alone [J10]. The unsupervised guide [J17] prescribes the same loop for the anomaly layer: flagged → operator disposition (true defect / false alarm / acceptable variation) → measured FP rate → refine. LOW/CODE [J12]: confirmed failures convert an unsupervised model into a supervised failure predictor over time.
- Weak supervision / active learning (MEDIUM, partly snippet-level): Snorkel DryBell's industrial-scale weak-supervision pattern (programmatic labeling functions from heuristics/legacy models/knowledge bases) is the documented template for scaling labels without hand-labeling everything [J-snippet]; semi-weakly supervised auto-labeling for bearings matched manual-label performance [J-snippet]; ALMAN active-learning architecture minimizes expert queries with budgeted oracle feedback [J-snippet, UNVERIFIED full text — claim held at snippet level]. None contradicts window-labels-first; all are positioned as upgrades once the loop exists.
- P-B answer: Phase 1 = free sim labels + steady-state-only normal set + shadow-mode dispositions as they accrue; Phase 2 = back-labeling algorithm (failure → earliest precursor) once real/operator labels exist; Phase 3 = weak-supervision labeling functions (state-gated heuristics as LFs) + budgeted active learning for rare faults. Never start with hand-labeling everything.

### T-P3. Imbalance in production: normal-only first, cost-aware seconds, per-asset thresholds always [→ P-C]

Consensus (HIGH):
- Normal-only deployment is the default production posture (extends T4): unsupervised models learn normal from good samples; no defect taxonomy needed to start; a test set of confirmed NOK parts is still required for threshold tuning [J17]. The ops guide's algorithm ladder is explicit: Isolation Forest first (no labels, sklearn, no ML specialist needed), SPC-ML for process/quality, autoencoders/LSTM only with 6–12 months data and ML engineering [J12].
- When supervision exists, cost-sensitivity beats resampling-alone: sklearn's official `TunedThresholdClassifierCV` post-tunes the decision cut-off against a business cost matrix via CV (German-credit demo: 5× miss cost) [J02]; production fraud/OT systems use multi-threshold decision bands (auto-approve / review / analyst / auto-decline) with per-band cost structures [J-snippet]; OT alert-cost work sets per-class thresholds minimizing expected cost [J-snippet]; the factory-floor hybrid used pos_weight 11.5 (≈92/8) with tiered alerting (conf>0.8 auto-work-order, 0.5–0.8 inspect, <0.5 log) — thresholds negotiated with the plant manager, not optimized [J15].
- In-pipeline resampling is MANDATED when used (official, non-negotiable): imbalanced-learn docs prove resampling the full dataset before splitting gives over-optimistic CV (0.724 vs 0.698 left-out) and prescribe `imblearn.pipeline` so resampling happens inside each fold (0.732 CV ≈ 0.727 left-out) [J01]; sklearn's pitfalls page generalizes it: never `fit` on test data; `fit_transform` on train, `transform` on test; Pipeline enforces it [J03].
- Thresholds are per-asset, not global: Merlion calibrates scores to z-scores with per-model `AggregateAlarms` (alm_threshold, suppression window, min-alarms-in-window) [J06]; fine-grained per-asset registration enables low-cost per-asset retraining [J-snippet]; equipment-type-specific models beat one generalized model by ~18pp precision in backtesting [J10 — vendor-reported, pattern-grade].
- P-C answer: default normal-only (IsolationForest-class or quantile detector) + fixed-percentile calibration (F1-Locked constraint); supervised complement uses class-weight/cost-sensitive loss + `TunedThresholdClassifierCV`-style post-tuning on a business metric; ANY resampling lives inside `imblearn.pipeline` with episode/seed-grouped splits; thresholds tuned per machine-class, never one global cut-off.

### T-P4. State/regime handling: filter transients from training, join downtime codes as context, model-per-regime when it pays [→ P-D]

Consensus (HIGH on filter-first; MEDIUM-HIGH on codes-as-context; MEDIUM on separate-models):
- Start-up/shutdown/changeover filtering is universal practice: baseline window = steady-state only; transients are normal machine behavior, not anomalies [J12]. Snippet-level production detail (UNVERIFIED full text): active-cycle isolation + fixed-length normalization per cycle, 10th-percentile current thresholds per station [J-snippet]; explicit startup/shutdown sample counts excluded so only steady-state trains/evaluates [J-snippet]; shutdown-startup detection delay tied to window size [J-snippet]. Our STARVED problem (29.5% of steps) is the mirror image at larger scale: a whole operating regime, not a transient edge.
- Downtime/oee codes are the join key (extends T4-G4): the MES reference design specifies the 3-layer model — states (Running/Starved/Blocked/Faulted/Changeover/Planned Stop) + timestamped event records + reason codes on segments — with threshold enforcement (<10–30 s auto-microstop, 30 s–3 min prompt, >15–30 min require reason + escalation) [J18]. Auto-coding is allowed ONLY when justifiable from signals; otherwise "Unclassified (review required)" [J18]. This is exactly the MAINT_EVENT/reset-flag mechanism Nebulaworks needed (Problem 4: post-overhaul vibration profile shift → history reset + suppression window, with CMMS event logging as the trigger) [J09].
- Filter vs feature vs separate models — evidence supports a ladder: (1) filter non-representative regimes from the normal baseline (cheapest, universal); (2) add state/regime as feature or context-gate (current draw "normal at full load, anomalous at idle" — enumerating every state as a rule doesn't scale, which is where the model earns its place [J13]); (3) separate models per equipment-type/regime when heterogeneity is large (the 18pp-precision result [J10, pattern-grade]). Generic single-model-across-regimes is the documented failure ("poor integration, generic data modelling" [01-C4]).
- P-D answer: STARVED/BLOCKED/DOWN excluded from the normal-training baseline by default (they are flow states, not equipment-normal); state carried as a feature + regime-conditioned thresholds at inference; per-class (A/B/C/ASM/RWK) models preferred over one global model; MAINT_EVENT-style reset flags + post-event suppression windows whenever a "maintenance" transition fires. The twin must export state + reason-code + event streams as stratification keys (back-propagate to generation).

### T-P5. Sim2Real fine-tuning: pretrain-synthetic → fine-tune-small-real is quantified; frozen-vs-full is domain-conditional [→ P-E indirectly; generation requirement]

Consensus (MEDIUM-HIGH, converging numbers):
- The paired-data budget is now quantified on industrial data: RF-DETR on 550 synthetic → near-perfect sim, 0.2516 mAP real; +50 PAIRED real (≈10% of synthetic) + 500 unpaired synthetic with k-DPP diversity sampling + KL embedding alignment → 0.8853 mAP [J19, Hitachi PHM-EU 2026]. Few-shot adaptation replicates: +10 real samples lifts 95.36→98.80 mAP@50 (random-texture) and 81.66→90.12 mAP@50-95 (PBR) [J-snippet]; 50 labeled real images ≈ 5% of real split used as calibration set in the T-LESS regime study [J-snippet].
- Frozen-backbone vs full fine-tune is domain-conditional, not a universal: frozen ImageNet features fail on subtle industrial defects off-manifold ("normal vs anomalous patches diverge from ImageNet manifolds" — ToCoAD motivation [J-snippet]); DINOv3 distillation shows no clear frozen-setting advantage on RGB, becoming consistently beneficial only after FULL fine-tuning, while X-ray behaves differently [J-snippet]. I.e., budget for full fine-tuning on sensory/RGB-grade twin signals; frozen linear probes are a diagnostic, not the recipe.
- The negative-transfer control exists: a CPS case study on pretraining-with-simulated-data for anomaly detection explicitly measures when sim pretraining helps vs hurts [J-snippet, UNVERIFIED full text — direction only, no numbers cited]. Domain randomization over photorealism (reflective parts) and never-claim-without-paired-real-validation carry over from T4 [01-I14b/c].
- Generation requirement back-propagated: keep FAULT_RANGES randomization (domain randomization = the transfer-relevant property); export paired-data hooks (seeded episode IDs so future real episodes can pair to sim episodes); plan fine-tune budget ≈ 5–10% paired real relative to synthetic volume.

### T-P6. Retraining + monitoring loop: evidence-triggered retrain, drift tracked independent of model output, maintenance events as first-class triggers [→ P-E]

Consensus (HIGH):
- Calendar retraining is insufficient — the single most-quoted operational lesson: "schedule-based retraining is not enough… retraining needs to be triggered by evidence, not by the calendar" [J09]. Implementations: weekly trailing-30-day metric job to CloudWatch with auto-triggered retraining pipeline [J09]; prediction-entropy + Jensen-Shannon class-distribution monitors with empirical thresholds (entropy 0.45/hr-window, JS 0.15 week-over-week) [J15]; Merlion's `TSADEvaluator` simulating live deployment with `retrain_freq="7d"` unsupervised retraining on recent data — weekly retraining raised ensemble precision 2/5→2/4 purely from drift adaptation [J06].
- Drift monitoring must be independent of model output: track raw-sensor statistics so shifts flag even before predictions go wrong [J11-postmortem]; separate "system health" SLOs from "output quality" SLOs [J-snippet/AugmentCode]; PSI baselined at deploy time and versioned with the artifact (warning 0.1–0.2 → Slack, critical >0.2 → pager) [J05].
- Maintenance/recalibration events are retraining/monitoring inputs, not invisible context: sensor recalibration changing baseline output caused a FP shutdown + a later miss — fix was versioning sensor metadata (calibration date/location/firmware) separately from readings [J11]; overhaul resetting vibration baseline caused 6 weeks of FPs — fix was CMMS-event-driven history reset + configurable suppression window [J09]; quarterly retraining on rolling 12-month windows + immediate-retrain triggers (new equipment, process change, new product/volume shift) [J12]; per-asset retraining on maintenance/replacement events [J-snippet].
- Data-version-driven automation is the tooling pattern: ClearML's TriggerScheduler clones the training task with overridden dataset ID whenever a new tagged ("Production") dataset version lands [J07]; MLflow's registry webhooks + scheduled drift checks decouple trigger policy from data selection [J04].
- P-E answer: monitor = trailing-window metrics job (weekly) + raw-input drift layer (PSI/KS vs deploy baseline) + sensor-health flags + MAINT_EVENT hook (reset + suppress); retrain triggers = metric-breach OR drift-breach OR maintenance-event OR new-regime — never calendar-only; automation = dataset-version trigger → retrain → evaluate vs production → promote/rollback (ClearML TriggerScheduler or MLflow webhook pattern).

### T-P7. Deployment + monitoring: alert budgets are the design constraint; shadow mode is non-negotiable; suppression lives outside the model [→ P-F indirectly; MINIPRO-10 shadow design]

Consensus (HIGH — the most replicated finding in this review):
- The alert budget is a hard input, not an output: "which method fits in five alerts a day and still catches the thing that matters" — 3σ on 200 metrics/min = 778 alerts/day [J-snippet]; on-call absorbs "a handful per shift" before muting everything [J13]; tune threshold to the budget FIRST, then read off recall; if recall-at-budget is too low, narrow scope, don't loosen the threshold [J13]. The 89%-FP vendor system (340 alerts, 38 real) was abandoned in 6 weeks and ran silently 11 months [J10]; the "85% accurate but muted" pattern recurs [01-C2].
- Shadow mode before live alerts is non-negotiable: 4–6 weeks observation-only, investigate would-be escalations, refine thresholds, THEN go live [J12]; 1–2 week shadow logging for alert rules with daily FP review [J05]; 2–4 weeks shadow vs incumbent alerting per Lookout-for-Metrics guidance [J-snippet]; backtesting (would-it-have-caught-last-year's-failures) + shadow are "the two most effective pre-production validation steps" [J05]. Direct input to MINIPRO-10's shadow cross-partition design.
- Suppression/grouping is plumbing, not modeling: three-tier architecture (early-warning / elevated / critical) with per-tier routing (trend report / CMMS 48-h window / SMS-to-tech) [J12]; deterministic suppression layer for known operational events BEFORE ML scoring [J-snippet]; deduplicate correlated alerts, hold self-resolving transients, roll related signals into one incident [J13]; pipeline-failure inhibition (suppress downstream accuracy alerts when the feature job failed — the drop is a symptom) [J05]; new-resource/cooldown suppression patterns [J-snippet].
- Precision-side acceptance (extends 01-C2): FP <2% on training before validation, <5% sustained; alert-to-confirmed >70%, lead time >48 h at 6 months [J12]; composite alerts (PSI-breach AND entropy-rise) as the precision lever [J05]; multi-signal corroboration (vibration+thermal+electrical) before high-priority alerts [J-snippet].
- Deployment-pattern answer: every detector ships with (budget, shadow log, suppression rules, tier routing, precision-side metrics) — the detector is the easy part; tuning + suppression + shadow validation are the engineering [J13].

## 5. Gaps & Contradictions (nothing suppressed)

- **GC1. Precision-vs-recall is THE contradiction, and recall-first loses (STRONG).** The 89%-FP system was rationally abandoned in 6 weeks [J10]; "85% accurate" models get muted [01-C2]; the budget-first tuning order (threshold-to-budget, then read recall) inverts textbook threshold selection [J13]. Challenge to us: quantile detectors + 4–7σ sim faults are sensitivity-tuned by construction; plants would reject them. Standing instruction: precision-side gates (alerts/1000 healthy windows, FP<5%, alert-to-confirmed>70%) ship WITH every detector; F1-Locked raw-F1 stays the ranking metric but never the only acceptance lens.
- **GC2. Simplicity-vs-platform contradiction (MEDIUM).** One factory ran the full MLflow+Kubeflow+DVC stack and concluded Airflow + Docker Compose would have sufficed; feature store, lineage tracking, and AutoML were all explicit overbuild for 15 features [J15]; a feature-store discovery-gap postmortem shows teams rebuilding features in the dark for six months [J-snippet]. Counter-position: MLflow tracking + registry + versioned Parquet is the floor (reproducibility/audit), Feast-style stores are the ceiling we do not need. Our pipeline spec must justify every component against student-team maintenance cost.
- **GC3. Sim-pretraining can hurt (MEDIUM, partly UNVERIFIED).** The CPS sim-pretraining impact study explicitly frames simulation gap as a risk to anomaly detectors, not just a free boost [J-snippet, PDF not opened — direction only]. Counter-position: the paired-data recipe (5–10% diverse paired real + embedding alignment) recovers 0.25→0.89 [J19]; domain randomization is the precondition [T4]. Rule: no sim-pretrained model promotes without paired-real validation; monitor for sim-gap drift as a first-class drift axis (P-E).
- **GC4. Model-complexity ladder contradicts "deeper is better" (MEDIUM).** LSTMs "overfitted terribly despite regularization"; XGBoost on hand features worked (74% recall); 1D-CNN-LSTM won barely (78% / 12% FPR vs 23%) [J15]; IsolationForest + SPC-ML recommended over autoencoders/LSTMs for first deployments [J12]. Supports M0b's quantile-vs-GDN-light framing: start simple, promote complexity only on measured gap.
- **GC5. Vendor numbers quarantined (disclosure).** $96M savings / 94% precision / 42% downtime [J10], 30%-faster UPW detection / 120k labor-hours [J-snippet], GE/PTC outcomes [01] — all unaudited vendor/hosted claims. Used ONLY for architecture patterns (FMEA-first, per-type models, confirmation windows, phased telemetry→context→pilot→agent sequencing). Never for effect sizes or ROI prose.
- **GC6. Generic models fail; context wins (MEDIUM-HIGH, corroborates 01-C4).** ~18pp precision gain from equipment-type-specific over generalized models [J10, pattern-grade]; per-asset registration + retraining [J-snippet]; "generic data modelling" as the named failure mode [01-C4]. Our per-class (A/B/C/ASM/RWK) modeling + topology mask is the same bet; a graph-free/generalized ablation stays on the battery as the honest control.
- **GC7. Retraining trigger debate is settled against the calendar (HIGH).** Evidence-triggered wins across 5 independent sources [J06, J09, J11, J12, J15]; calendar-only is the documented failure ("flying blind between runs" [J09]). No live counter-position found — logged as consensus, not contradiction.
